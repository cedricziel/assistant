# Feature Specification: Backup and Restore Subcommands

**Feature Branch**: `004-backup-restore`
**Created**: 2026-03-29
**Status**: Draft
**Input**: User description: "users should be able to use a subcommand for backing the installation up and another one for restoring. for this one, its paramount that we create a testable implementation"

## User Scenarios & Testing _(mandatory)_

### User Story 1 - Back Up the Current Installation (Priority: P1)

A user wants to create a complete snapshot of their assistant installation — including all personas, skills, configuration, and stored data — so they can recover from accidental changes, migrate to a new machine, or safely experiment with configuration changes.

**Why this priority**: Without the ability to produce a backup, restore is meaningless. This is the foundational operation that everything else depends on.

**Independent Test**: Can be tested end-to-end by running the backup subcommand and verifying that a well-formed archive is produced at the expected location containing all required installation artifacts.

**Acceptance Scenarios**:

1. **Given** a configured installation, **When** the user runs `assistant backup`, **Then** a backup archive is created at a known, predictable path that is reported to the user upon success.
2. **Given** a configured installation, **When** the user runs `assistant backup --output /custom/path/backup.tar.gz`, **Then** the archive is written to the specified path.
3. **Given** a configured installation, **When** the backup completes successfully, **Then** the archive contains all personas, skills, configuration, and the SQLite database(s).
4. **Given** a running installation, **When** a backup is created, **Then** the source installation is left unmodified.
5. **Given** an invalid output path (e.g., directory does not exist), **When** the user runs the backup subcommand, **Then** an actionable error message is displayed and no partial archive is left behind.

---

### User Story 2 - Restore from a Backup Archive (Priority: P2)

A user wants to revert their assistant installation to a previously backed-up state — for example after an upgrade went wrong, data was accidentally deleted, or they are setting up the assistant on a new machine from an existing backup.

**Why this priority**: Restoring from backup is the primary recovery mechanism; it depends on backup being available first.

**Independent Test**: Can be tested in isolation by pointing the restore subcommand at a pre-created archive (generated by the backup subcommand or crafted in tests) and asserting the installation state matches the archive contents.

**Acceptance Scenarios**:

1. **Given** a valid backup archive, **When** the user runs `assistant restore /path/to/backup.tar.gz`, **Then** all artifacts from the archive are written to the installation directory, replacing any existing files.
2. **Given** a valid backup archive and an existing installation, **When** restore completes, **Then** the restored state is identical to the state at the time of the backup.
3. **Given** a corrupted or incomplete archive, **When** the user attempts a restore, **Then** an actionable error is displayed, the restore is aborted, and the existing installation is left intact.
4. **Given** a backup archive produced by an older version, **When** the user restores, **Then** the restore either succeeds with a compatibility note or fails with a clear version mismatch error (no silent data loss).
5. **Given** a restore that is about to overwrite an existing installation, **When** the user has not passed a `--force` flag, **Then** the user is prompted to confirm before any files are modified.

---

### User Story 3 - List and Inspect Available Backups (Priority: P3)

A user who keeps multiple backups wants to identify which archive to restore from without having to remember filenames or creation times.

**Why this priority**: Discoverability is a usability improvement; backup and restore work without it.

**Independent Test**: Can be tested by creating one or more archives, running `assistant backup list`, and asserting the output includes expected metadata (creation date, size, archive path).

**Acceptance Scenarios**:

1. **Given** one or more backup archives in the default backup directory, **When** the user runs `assistant backup list`, **Then** each archive is listed with its creation timestamp, size, and path.
2. **Given** no backups in the default directory, **When** the user runs `assistant backup list`, **Then** an informative empty-state message is displayed.

---

### Edge Cases

- What happens when the installation directory is partially written (mid-backup crash)? The incomplete archive must be deleted; the source must remain intact.
- What happens when the target restore directory already contains data but no existing backup exists to merge with? The user must explicitly confirm overwrite via `--force` or an interactive prompt.
- What happens when available disk space is insufficient for the archive? The operation must fail early with a disk-space error before writing partial data.
- What happens when a backup archive references files that no longer exist at restore time (e.g., externally referenced skill paths)? Files present in the archive are restored; missing external references are reported as warnings, not errors.
- What happens when the same backup subcommand is invoked concurrently? Only one operation should proceed; the second must fail with a clear conflict error.

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: The system MUST provide a `backup` subcommand that produces a self-contained archive of the entire installation.
- **FR-002**: The system MUST include all personas, skills, configuration files, and SQLite database(s) in the backup archive.
- **FR-003**: The `backup` subcommand MUST write archives to a default location under the user's installation directory when no output path is specified, and to a user-supplied path when `--output` is given.
- **FR-004**: The `backup` subcommand MUST report the output path, archive size, and a success/failure status to the user upon completion.
- **FR-005**: The system MUST provide a `restore` subcommand that accepts a path to a backup archive and restores the installation to the state captured in that archive.
- **FR-006**: The `restore` subcommand MUST abort and leave the existing installation intact when the provided archive is missing, corrupted, or fails integrity validation.
- **FR-007**: The `restore` subcommand MUST require explicit user confirmation (interactive prompt or `--force` flag) before overwriting an existing installation.
- **FR-008**: The backup archive format MUST be deterministic and inspectable (e.g., a standard compressed archive), enabling testing without running the live CLI.
- **FR-009**: Both subcommands MUST be implemented in a way that the core backup/restore logic is independently testable as a library function, separate from CLI argument parsing.
- **FR-010**: The system MUST validate the archive integrity before and after creation (checksum or equivalent), reporting any discrepancy to the user.
- **FR-011**: The `restore` subcommand MUST detect and report version mismatches between the archive and the current installation, without performing silent data loss.
- **FR-012**: The system MUST clean up any partial or temporary files on failure of either the backup or restore operation.

### Key Entities

- **Backup Archive**: A self-contained file capturing the complete installation state at a point in time. Key attributes: creation timestamp, version tag, content manifest, integrity checksum.
- **Installation Directory**: The root directory holding all mutable assets (personas, skills, configuration, databases). The source for backup and target for restore.
- **Backup Manifest**: A machine-readable index inside the archive listing included artifacts, their original paths, sizes, and checksums. Enables integrity verification and version detection.

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: A user can create a full backup of their installation in under 30 seconds for a typical installation (up to 100 personas, 50 skills, database up to 50 MB).
- **SC-002**: A user can restore from a valid backup in under 60 seconds for the same typical installation size.
- **SC-003**: 100% of artifacts present at backup time are present and byte-identical after a round-trip backup → restore → verify cycle.
- **SC-004**: All backup and restore core logic (excluding CLI argument parsing) is covered by automated unit or integration tests that can run without a live installation.
- **SC-005**: A corrupted or truncated archive causes restore to abort with a non-zero exit code and a human-readable error message in 100% of test cases.
- **SC-006**: No partial or temporary files remain on disk after a failed backup or restore operation in 100% of test cases.

## Assumptions

- Users have write access to the installation directory and to the backup output path.
- The installation state fits on a single machine's local filesystem; distributed or cloud-backed installations are out of scope for this feature.
- The SQLite database(s) can be safely copied while the assistant is not actively writing to them; concurrent-write safety during backup is a future concern.
- A "typical installation" is defined as: up to 100 personas, 50 skills, and a database no larger than 50 MB.
- The backup archive will use a standard compressed format to maximize inspectability and cross-platform compatibility.
- Mobile support and remote/cloud backup destinations are out of scope for this version.
- The interactive confirmation prompt for restore is skippable with a `--force` flag to support automated/scripted usage (e.g., CI restore pipelines).
