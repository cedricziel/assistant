## Why

The assistant already supports vision — Anthropic and OpenAI providers can process `ContentBlock::Image` — but there is no way for users to actually send images. Chat interfaces like Slack and Matrix already download image attachments from their platforms, yet discard them before they reach the LLM. The web UI and Flutter app have no upload mechanism at all.

Users want to share screenshots, photos, diagrams, and other visual context with the assistant across every interface.

## What Changes

- Add `AttachmentMeta` type to `assistant-core` (persisted metadata, no bytes)
- Add `AttachmentStore` to `assistant-storage` (filesystem writes + SQLite metadata)
- New migration: `message_attachments` table (metadata only, no BLOBs)
- Extend `TurnRequest` with `attachment_ids: Vec<Uuid>` (IDs only, bus stays lightweight)
- Runtime loads attachment bytes from disk and builds `ContentBlock::Image` when calling LLM providers
- New authenticated endpoint: `POST /api/conversations/{id}/attachments` — multipart upload, returns attachment metadata
- New authenticated endpoint: `GET /api/attachments/{id}` — serves the image file with correct Content-Type
- Attach metadata to SSE message events so the Flutter app can render inline images
- Wire Slack `file_share` and Matrix `m.image` events through `AttachmentStore` instead of discarding them
- Outbound: tool-generated images (bash, DALL-E, MCP, skills) are persisted via `AttachmentStore` and delivered to users — uploaded to Slack/Matrix, rendered inline in web UI
- `TurnResult.attachments` changes from `Vec<Attachment>` (bytes) to `Vec<Uuid>` (IDs) — bus stays lightweight in both directions
- Flutter: image picker button in chat input, thumbnail preview before send, inline image rendering in chat bubbles (both user and assistant messages)

## Storage Design

Images are stored on the filesystem, scoped by persona and conversation:

```
~/.assistant/agents/{agent_id}/attachments/{conversation_id}/{attachment_id}.{ext}
```

SQLite holds only metadata (id, message_id, conversation_id, agent_id, filename, mime_type, size_bytes, created_at). No BLOBs in the database.

## Capabilities

### New Capabilities

- `image-upload`: Users can attach images to messages via the web UI, Flutter app, or chat interfaces (Slack, Matrix). Images are persisted to disk and their metadata is stored in SQLite.
- `image-vision`: User-provided images are forwarded to vision-capable LLM providers as `ContentBlock::Image`, enabling the assistant to see and reason about visual content.
- `image-serving`: Uploaded images are served back to clients via an authenticated API endpoint with on-demand resizing and disk-cached variants for inline rendering in chat history.
- `image-outbound`: Images generated by tools (bash scripts, image generation APIs, MCP tools, skills) are persisted through the same `AttachmentStore` and delivered to users across all interfaces.

### Modified Capabilities

- `chat-send`: The message sending flow gains an optional attachment step. Text-only messages continue to work unchanged.

## Impact

**Rust crates:**

- `assistant-core`: new `AttachmentMeta` struct, supported MIME type constants, validation helpers
- `assistant-storage`: new `AttachmentStore` (filesystem + SQLite), new migration for `message_attachments` table
- `assistant-core` (bus): `TurnRequest` gains `attachment_ids: Vec<Uuid>`
- `assistant-runtime`: orchestrator loads attachment bytes from `AttachmentStore`, builds `ChatHistoryMessage::MultimodalUser` with `ContentBlock::Image` blocks
- `assistant-web-ui`: new `POST /api/conversations/{id}/attachments` (multipart, authenticated), new `GET /api/attachments/{id}` (authenticated, streams file), attachment metadata included in message SSE events
- `assistant-interface-slack`: wire `file_share` image downloads through `AttachmentStore`
- `assistant-interface-matrix`: wire `m.image` downloads through `AttachmentStore`

**Flutter app:**

- Image picker integration (camera + gallery on mobile, file picker on web/desktop)
- Multipart upload to attachments endpoint
- Thumbnail preview in chat input before sending
- Inline image rendering in chat message bubbles
- Tap-to-expand full-size image viewer

**OpenAPI / codegen:**

- New schemas: `AttachmentMeta`, multipart upload spec
- Regenerate Flutter API client after spec update

## Non-Goals (this change)

- Storing BLOBs in SQLite
- LLM integration for non-image file types (PDFs, CSVs) — storage and API are file-type-agnostic from day one, but the LLM content-block bridge and resize pipeline only handle images initially. Adding PDFs etc. is an incremental follow-up, not a rearchitecture.
- Image-to-image generation or editing
- Attachment cleanup / garbage collection (can be added later)
- Mattermost, Nextcloud, or Signal image support (can follow once the core path is proven with Slack + Matrix)

## Decisions

- **Resize strategy**: Resize at LLM-call time, not on ingest. Store originals on disk at full quality. The runtime resizes per provider limits (Anthropic ~5 MB, OpenAI ~20 MB) when building the LLM request. Upload cap of 10 MB prevents abuse.
- **Ollama vision**: Always include images in the request. Warn the user that the selected model may not support vision.
