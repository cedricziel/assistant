## Context

The web-UI crate (`crates/web-ui`) exposes its REST surface as an OpenAPI 3 document via `utoipa`. The committed snapshot at `openapi.json` is the contract that drives:

- The Flutter app's generated dio client (`app/packages/assistant_api/`, regenerated by `make generate-flutter-client`).
- Any third-party tooling reading the spec.

Today's reality:

- **Inconsistent 401 coverage.** A grep across `crates/web-ui/src/api/*.rs` shows uneven `(status = 401, ...)` blocks: 14/15 in `mod.rs` (conversations), 10/10 in `personas.rs`, **0/5 in `spaces.rs`**, **0/5 in `users.rs`**, **0/4 in `members.rs`**, **0/7 in `catalog.rs`**, **0/3 in `interfaces.rs`**. The new multi-org endpoints landed without 401 docs.
- **Inconsistent body shape.** `AGENTS.md` says all errors use `{"error": "...message..."}`, but several handlers return plain strings: e.g. `(StatusCode::FORBIDDEN, "access denied").into_response()` in `api/spaces.rs:104`. Others use `Json(serde_json::json!({"error": "..."}))`. The OpenAPI doc at `crates/web-ui/src/openapi.rs:152` defines a _third_ shape `ApiErrorResponse { code: i32, message: String }` that no handler actually returns.
- **No CI enforcement.** Nothing fails when a new endpoint forgets `responses(401)` or returns a plain-string body.

The just-landed `flutter-401-and-space-selector-fixes` interceptor matches on `statusCode == 401` and does not parse error bodies, so this cleanup is independent of that change. But the _next_ consumer (a Python SDK, a webhook receiver, a UI banner that wants to show the server message) needs the body shape to be a contract, not a coin flip.

## Goals / Non-Goals

**Goals:**

- One error body shape across the entire `/api/...` surface: `{"error": "...message..."}` (matches `AGENTS.md`).
- One schema in OpenAPI: `ErrorBody`. Every documented 4xx/5xx response on a secured endpoint references it.
- Every endpoint that declares `security(("bearer_token" = []), ...)` MUST list a `401` response (with `body = ErrorBody`).
- A Spectral ruleset committed at the repo root, runnable locally (`make lint-openapi`) and in CI, that fails the build on missing 401 coverage or wrong body schema.
- Zero status-code changes — the wire behavior of every endpoint stays as it is today.

**Non-Goals:**

- Generic envelope for non-secured endpoints (e.g., `/oauth/*`). The OAuth endpoints follow RFC 6749 §5.2 (`{error, error_description, error_uri}`) and stay verbatim.
- Per-response typed Dart error classes. The dio generator template doesn't support that, and the Flutter interceptor doesn't need it.
- Rewriting handlers to use `Result<T, ApiError>` with a custom rejection — out of scope; we keep the imperative `(StatusCode, Json(...))` style and just standardize the body.
- Adding 4xx schemas to every existing 400/403/404/409/etc. response in one go. We add `ErrorBody` to `401` everywhere (the focus of this change) and to `403` where the security spec requires it. Other status codes can be back-filled opportunistically without blocking this change.

## Decisions

### Decision 1: A single `ErrorBody { error: String }` schema

Define in `crates/web-ui/src/openapi.rs`:

```rust
#[derive(serde::Serialize, utoipa::ToSchema)]
pub struct ErrorBody {
    /// Human-readable error message.
    pub error: String,
}
```

Add it to the `components(schemas(...))` macro list. Mark the existing `ApiErrorResponse { code, message }` as `#[deprecated]` and remove it from the schemas list once no handler references it; it appears unused outside the schema registry today, so removal is one commit.

**Why not `{code, message}`?** Because every handler that already follows the convention writes `{"error": ...}`. The rename direction was decided years ago in `AGENTS.md`; we align the schema with the code, not the other way around.

**Alternatives:** Adding `code: Option<String>` for machine-readable error keys. Rejected — no caller uses it, no handler emits it, and we don't want to design that surface in this change. Easy follow-up if needed.

### Decision 2: One server-side helper to enforce the envelope

Add `crates/web-ui/src/errors.rs`:

```rust
pub fn json_error(status: axum::http::StatusCode, message: impl Into<String>) -> axum::response::Response {
    use axum::{Json, response::IntoResponse};
    (status, Json(serde_json::json!({"error": message.into()}))).into_response()
}
```

Used everywhere a handler currently writes either `(StatusCode::X, "plain text").into_response()` or `(StatusCode::X, Json(serde_json::json!({"error": "..."}))).into_response()`. The first case becomes a behavior change (plain → JSON); the second is a no-op refactor for readability.

**Why not a Rejection-style typed error?** Would require touching every handler's signature. Out of scope; the helper achieves the same observable contract with surgical edits.

### Decision 3: Sweep 401 (and obvious 403) across every secured endpoint

Define a tiny utoipa fragment we can paste consistently:

```rust
responses(
    (status = 200, ..., body = SomeType),
    (status = 401, description = "Unauthorized", body = ErrorBody),
    (status = 403, description = "Forbidden", body = ErrorBody),  // only if the handler emits 403
    ...
)
```

We do not auto-add 403 to every secured endpoint — only those whose code path actually returns 403 (e.g., role checks). The Spectral rule below enforces 401, not 403.

### Decision 4: Spectral ruleset for CI

New file `openapi-spectral.yaml` at repo root:

```yaml
extends: ["spectral:oas"]
rules:
  # Every operation that requires auth MUST document a 401 response.
  secured-operations-document-401:
    description: "Operations declaring a bearer/oauth security requirement must list a 401 response."
    given: "$.paths[*][?(@.security && @.security.length > 0)]"
    severity: error
    then:
      field: "responses.401"
      function: truthy
  # The 401 response body MUST reference our shared envelope.
  401-uses-error-body:
    description: "The 401 response must use the ErrorBody schema."
    given: "$.paths[*][*].responses.401.content.application/json.schema"
    severity: error
    then:
      field: "$ref"
      function: pattern
      functionOptions:
        match: "ErrorBody$"
```

CI: add a job to `.github/workflows/ci.yml` (or a new `openapi.yml`) that runs:

```yaml
- name: Lint OpenAPI
  run: |
    npm install -g @stoplight/spectral-cli
    spectral lint openapi.json --ruleset openapi-spectral.yaml --fail-severity=error
```

Add a `make lint-openapi` Make target so contributors can run it locally without thinking about the CLI invocation.

**Why Spectral over a custom Rust validator?** Spectral is the de-facto OpenAPI linter, the rule syntax above is declarative, and our spec is small enough that lint runs in <1s. A custom Rust validator would be more work for a worse experience.

**Why fail-severity=error?** We want this to break the build, not produce warnings nobody reads. Existing operation-level security warnings from `spectral:oas` (e.g., missing operation IDs) are not in scope and may be set to `severity: hint` if they fire too noisily on the current spec.

### Decision 5: Regenerate the Flutter client as part of this change

After the server-side sweep, run `make dump-openapi && make generate-flutter-client` and commit the regenerated files under `app/packages/assistant_api/`. The diff should be small (response models pick up the `ErrorBody` schema) and uncontroversial.

## Risks / Trade-offs

- **Plain-text → JSON body shift on a few endpoints** breaks anyone parsing error bodies as strings → mitigated: nothing in the Flutter app, the test suite, or known external consumers parses error bodies. A line in the changelog covers the contract change.
- **Spectral CI flakiness from npm install on every run** → mitigate by pinning `@stoplight/spectral-cli` to a version and caching `~/.npm` (existing CI cache pattern in `.github/workflows/ci.yml`).
- **Regenerating `assistant_api/` produces a large diff** that obscures the actual change → mitigate by splitting into two commits in the same PR: `chore(web-ui): standardize 401 envelopes` and `chore(api-client): regenerate from updated spec`.
- **Spectral rule too aggressive** (e.g., flags an internal-only path) → escape hatch via Spectral overrides per-path, but we do not pre-emptively add overrides; we let the first run tell us if any operation needs one.
- **`OAuthErrorResponse` looks like an error envelope but isn't** → comment in `openapi.rs` documenting that it's RFC 6749 §5.2 verbatim and intentionally separate.

## Migration Plan

1. Land the schema + helper + sweep in one PR (split commits as noted in the regeneration risk above).
2. Re-run `make dump-openapi` and commit `openapi.json`.
3. Re-run `make generate-flutter-client`; commit the regenerated client.
4. Add the Spectral rule and CI step. Run `make lint-openapi` locally before opening the PR — must pass.
5. Merge. No deploy gating; this only affects the web-ui crate, which is rebuilt on every release.
6. **Rollback**: revert. The schema and helper are additive; the body shape change can be re-verted file-by-file if a downstream consumer surfaces.

## Open Questions

- Should `ErrorBody` carry an optional `code` field for machine-readable error identifiers? Defer — start with `{"error": ...}` matching reality. Add later if a typed-error use case shows up.
- Should we apply the Spectral rule to `403` too, or keep it 401-only? Recommend 401-only in this change, then file a follow-up to expand once the 401 coverage is green.
- Should the helper live in `crates/web-ui/src/errors.rs` or in `assistant-core` so other crates can use it? Web-ui only for this change — the helper depends on `axum::Response`, which is a web-ui concern.
